# Design Decisions

## Step 1: Project skeleton

- **Configuration via environment variables.** Secrets and settings live in `.env`
  (never committed). `.env.example` documents the variables the project needs.
- **API versioning from day one.** All routes live under `/api/v1`, so a future
  breaking change can ship as `/api/v2` without breaking existing clients.
- **Layered structure.** `api/` handles HTTP and `core/` holds configuration.
  Business logic will live in `services/` and database code in `models/`, so each
  part stays small and easy to test.
- **Docker Compose for local development.** One command starts the API and
  PostgreSQL. The database has a healthcheck, so the API only starts once
  Postgres accepts connections.
- **Pinned dependency versions.** Everyone gets the same versions, so builds are
  reproducible.
- **Configurable pip index.** The Dockerfile takes a `PIP_INDEX_URL` build
  argument that defaults to the official PyPI. Developers on restricted networks
  can override it in their local `.env` (never committed) without changing the
  Dockerfile or affecting CI.

## Step 2: Database connection

- **SQLAlchemy 2 with the psycopg 3 driver.** SQLAlchemy is the standard ORM in
  the Python ecosystem. The `[binary]` build of psycopg bundles libpq, so the
  Docker image needs no extra system packages.
- **No default value for `DATABASE_URL`.** If it is missing, the app refuses to
  start instead of silently connecting to the wrong database (fail fast).
- **One session per request.** `get_db` is a FastAPI dependency that opens a
  session and always closes it in a `finally` block, so connections are never
  leaked from the pool.
- **`pool_pre_ping=True`.** The pool checks a connection before using it, so the
  API recovers on its own after a database restart.
- **Separate health checks.** `/health` only says the API process is up.
  `/health/db` also queries the database and returns 503 (not a crash with 500)
  when it is down.
- **Verified manually.** With the database container stopped, `/health` stays
  200 and `/health/db` returns 503. After the database restarts, `/health/db`
  returns 200 again without restarting the API.

## Step 3: Data model and migrations

- **Three tables: `users`, `events`, `bookings`.** Small on purpose. Payments,
  ticket tiers and seat maps can be added later through migrations.
- **Alembic from day one.** Every schema change is a versioned file in git, so
  any database can be rebuilt with `alembic upgrade head`. Autogenerated
  migrations are drafts and are read before they run.
- **Single source for the database URL.** `alembic/env.py` reads
  `settings.database_url`, so `alembic.ini` contains no credentials.
- **Named constraints.** A naming convention on `Base.metadata` gives every
  constraint a predictable name. Future migrations can drop or change them, and
  database errors are readable.
- **Money as integers.** Prices use the smallest currency unit to avoid
  floating point errors. `bookings.total_price` is a snapshot of the price at
  purchase time, so later price changes do not rewrite history.
- **Rules enforced by the database.** CHECK constraints (stock never negative,
  available <= total, positive quantity, valid status) and foreign keys hold
  even if application code has a bug. Verified with raw SQL: invalid rows were
  rejected and nothing was stored.
- **Status as a CHECK constraint, not a database enum.** Adding a new status
  later is a simple migration.
- **Bookings are cancelled, never deleted.** A booking changes `status` and the
  row stays. Foreign keys have no cascade, so users and events that have
  bookings cannot be deleted.
- **Indexes on foreign keys.** PostgreSQL does not create them automatically,
  and lookups by user or event would slow down as bookings grow.
- **Timestamps in UTC, set by the database.** `timestamptz` with `now()`, so
  every API instance gets its time from the same source.

## Step 4: Authentication

- **Passwords are hashed with argon2 (pwdlib).** Plain passwords are never stored.
  Argon2 is deliberately slow and every hash gets its own salt.
- **Short-lived JWT access tokens (30 minutes), signed with HS256.** The payload
  holds only the user id (`sub`) and the expiry (`exp`). The role is not in the
  token: the user is loaded from the database on every request, so a role change
  applies immediately.
- **`SECRET_KEY` has no default value.** The app refuses to start without it,
  instead of running with a guessable key.
- **Strict token validation.** Decoding pins the allowed algorithm and requires
  `exp` and `sub`, so a token without an expiry is rejected. Expired, forged and
  malformed tokens all return the same 401.
- **No user enumeration on login.** An unknown email and a wrong password return
  the same 401 message. When the email does not exist, the password is verified
  against a dummy hash, so both cases take a similar time.
- **Separate input and output schemas.** `UserCreate` accepts only email and
  password, so a client cannot choose its own role. `UserRead` has no
  `hashed_password`, so the hash never leaves the API. Registration always
  creates the role `user`.
- **Emails are normalized to lowercase** before they are stored or looked up.
- **Duplicate emails are caught by the database constraint.** The service
  catches `IntegrityError` and raises its own error, and the endpoint maps it to
  409. There is no check-then-insert race.
- **Business logic lives in `services/`.** The service knows nothing about HTTP.
  Endpoints translate service errors into status codes.
- **OAuth2 password flow with form login.** Login reads a form (`username` is the
  email), so the Authorize button in Swagger UI works.
- **No token revocation yet.** A token stays valid until it expires. The short
  lifetime limits the damage. Refresh tokens or a deny list can be added if
  needed.

## Step 5: Events

- **Reads are public, writes are admin-only.** The `GET` endpoints need no
  token. `POST`, `PATCH` and `DELETE` use `dependencies=[Depends(require_admin)]`,
  so the check lives in one place and runs before the handler. A normal user
  gets 403 even for an event id that does not exist, so ids cannot be probed.
- **Separate schemas for create, update and read.** On creation the server sets
  `available_tickets` equal to `total_tickets`. `total_tickets` cannot be
  edited, because changing capacity interacts with tickets already sold.
- **PATCH only touches fields the client sent.** `exclude_unset` tells "not
  sent" apart from "sent as null". Null is rejected for required fields and
  allowed for `description`.
- **Events with bookings cannot be deleted.** The foreign key has no cascade.
  The service turns the database error into its own exception and the endpoint
  returns 409. A soft delete (a status column) is the likely next step.
- **Pagination with `limit` and `offset`.** `limit` is capped at 100 so one
  request cannot pull the whole table, and the response carries `total`.
  Results are ordered by `(starts_at, id)`. The `id` tie-breaker keeps the
  order deterministic, so rows are not duplicated or skipped between pages.
  Known weakness: rows inserted between two page requests shift the offset.
  Cursor pagination would fix that if it ever matters.
- **One filter function for count and items.** `q`, `upcoming` and
  `available_only` are applied by `_apply_filters` to both queries, so `total`
  always matches the filtered result.
- **Safe text search.** `q` is capped at 100 characters and matched with
  `ILIKE`. The characters `%` and `_` are escaped so they are searched
  literally instead of acting as wildcards.
- **Filters are opt-in.** All defaults are off, so clients never get silently
  filtered results.
- **"Now" comes from the database** (`now()`), like every timestamp, so all API
  instances share one clock.

## Step 6: Bookings and overselling protection

- **Check and decrement happen in one conditional UPDATE.** Reading the stock in
  Python and writing it back is a race condition. In a deliberately naive
  version, 12 parallel requests for 5 tickets created 12 bookings and left
  `available_tickets` wrong, with no error. The real code runs
  `UPDATE events SET available_tickets = available_tickets - n WHERE id = ? AND
  available_tickets >= n AND starts_at > now()`. PostgreSQL locks the row, so a
  waiting request re-checks the condition against the new value. The same test
  now produces exactly 5 bookings and 7 rejections.
- **Reserving tickets and creating the booking are one transaction.** If the
  insert fails, the rollback gives the tickets back. Verified with an unknown
  user id: the request failed and `available_tickets` stayed unchanged.
- **Cancelling is guarded the same way.** The booking is switched to
  `cancelled` by an UPDATE with `WHERE status = 'confirmed'`, and tickets are
  returned only if that UPDATE changed a row. In a naive version, two parallel
  cancels returned the tickets twice (10 available + 3 still booked = 13 tickets for a capacity
  of 10). With 8 parallel cancels exactly one succeeds and the total stays 10.
- **CHECK constraints are a second line of defense, not the fix.** The naive
  versions passed them, because the corrupted values were still between 0 and
  the capacity. The conditional UPDATE is what prevents the bug.
- **After a failed UPDATE, the service asks why.** That query only chooses the
  error: event not found (404), event already started (409) or not enough
  tickets (409). It changes no data.
- **The server decides price and owner.** `BookingCreate` has only `event_id`
  and `quantity`. The price comes from the same UPDATE that reserves the
  tickets, and the user id comes from the token.
- **`total_price` is a snapshot.** Later price changes do not affect existing
  bookings. Free events have price 0, so the code checks `price is None`, not
  `not price`.
- **Users only see their own bookings.** `GET /bookings` takes the user id from
  the token and the URL has no user id, so a user cannot read someone else's
  bookings by guessing ids. Cancelling another user's booking returns the same
  404 as a missing booking, so ids cannot be probed.
- **Bookings are cancelled, never deleted.** Cancelling is
  `POST /bookings/{id}/cancel`. The row stays and its status changes. A
  cancelled booking still appears in the user's list.
- **Cancelling twice returns 409.** This is a deliberate choice for clearer
  errors. An idempotent 200 would be easier for clients that retry.
- **At most 10 tickets per booking.** A product rule that is easy to change.
- **Known limitations.** There is no idempotency key, so a double click creates
  two bookings and the user can cancel one. Bookings for the same event queue
  on one row lock, which is fine at this scale. The concurrency tests were run
  by hand and are the first candidates for automated tests.

## Step 7: Automated tests

- **Tests run against real PostgreSQL, not SQLite.** The important guarantees
  of this project (row locks, CHECK constraints, conditional UPDATEs with
  `RETURNING`, `now()`) only exist in PostgreSQL. A fake database would let the
  tests pass while the real one fails.
- **A separate test database.** Its URL comes from `TEST_DATABASE_URL`, or from
  `DATABASE_URL` with `_test` added to the database name. The tests refuse to
  run if the name does not end with `_test`, because every run drops that
  database. A typo can never wipe development data.
- **The schema is built by the real migrations.** Each run recreates the test
  database and runs `alembic upgrade head`, so the migrations are tested too,
  not only the models.
- **Every test starts from empty tables.** After each test the tables are
  truncated and ids restart from 1, so tests never depend on each other or on
  their order.
- **Mostly black-box HTTP tests.** Tests call the API with FastAPI's
  `TestClient` and check status codes and JSON, the same contract a client
  sees. Test data that the API cannot create on purpose (events in the past,
  sold-out events, admin users) is inserted directly through the models.
- **The manual checks from earlier steps are now automated.** Overselling,
  double cancel, user enumeration on login, id probing, forged and expired
  tokens, `%` and `_` in search, pagination without duplicates, the CHECK
  constraints, and `/health/db` returning 503 when the database is down.
- **Concurrency tests use real threads and separate sessions.** A barrier
  releases all threads at the same moment, so they really compete for the same
  row. Only plain ids cross into threads, because a SQLAlchemy session must
  never be shared between threads. Unexpected exceptions are recorded instead
  of being lost, so a failure shows its real cause.
- **The concurrency tests were checked against the naive code.** With the old
  read-then-write version of `create_booking`, the test reported 12 bookings
  for 5 tickets. With the naive cancel, parallel cancels tried to return the
  tickets more than once. With the real code both tests pass. A test that
  cannot fail proves nothing.
- **Test tools are not in the production image.** `requirements-dev.txt` adds
  pytest and httpx on top of `requirements.txt`. The Dockerfile installs them
  only when the `INSTALL_DEV` build argument is `true`, which
  `docker-compose.yml` sets for local development.

## Step 8: Continuous integration

- **Every push to `main` and every pull request runs the checks on GitHub
  Actions.** A change that breaks something is visible on the pull request
  before it is merged.
- **The tests use a real PostgreSQL 16 service container,** the same version
  as `docker-compose.yml`. The job waits for its healthcheck before starting.
- **Migrations are checked in both directions.** `alembic upgrade head`, then
  `alembic check` (fails if a model was changed without a migration), then
  `alembic downgrade base` and `upgrade head` again. A forgotten or broken
  migration fails the build.
- **The Docker images are built in CI.** Both the production image and the
  development image (with the test tools) must build, so a broken Dockerfile
  is caught even though the tests themselves run without Docker.
- **CI has its own throwaway secrets.** The database password and
  `SECRET_KEY` in the workflow are used only by the temporary CI database.
  Real secrets never go into the repository.
- **Pip downloads are cached** by the hash of the requirements files, so most
  runs skip the downloads.
